# SGLang Profiler Viewer

A local web application that reads profile logs generated by SGLang
`bench_serving --profile`, continuously discovers newly generated profile files,
maps low-level profiler events to understandable SGLang concepts / source-code
locations, and renders the profiling result as an easy-to-understand semantic
timeline.

> **The viewer explains the profiler data instead of merely displaying it.**
> Raw kernel names such as `flashinfer::BatchPrefillWithPagedKVCacheKernel<…>`
> are mapped to semantic operations (Attention, RMSNorm, RoPE, KV Cache, GEMM,
> MLP, Sampling, …) with a link back to the SGLang source that launches them.
> The original raw event is always preserved and inspectable.

See `spec/project-scope-specification.md` (what) and `spec/techical-spec.md`
(how) for the full requirements.

---

## Architecture

```
Browser (React + TypeScript + Vite + Tailwind + D3)
        │  HTTP (REST)  +  WebSocket (live updates)
        ▼
Python backend (FastAPI + Uvicorn + watchdog)
  ├─ ProfileManager   registry, scan, file-stability, LRU cache
  ├─ FileWatcher      watchdog observer on the profile root
  ├─ TraceParser      gzip + JSON → normalized events
  ├─ StepDetector     step[STAGE bs=N toks=M] annotations → steps
  ├─ SemanticMapper   declarative YAML rules (mappings/)
  ├─ SourceMapper     semantic rule → SGLang source reference
  └─ Aggregator       per-step metrics (wall / GPU-busy / per-category)
        │
        ▼
Profile directory  (PROFILE_ROOT)  →  *.json.gz
```

The frontend is built to `frontend/dist` and served by the backend, so a single
process serves both the API and the UI.

## Quick start

### One-command run (recommended)

`run.sh` builds the frontend (if needed) and starts the backend in one step:

```bash
./run.sh               # build frontend (if stale/missing) + start backend
./run.sh --no-build    # skip the frontend build, just start the backend
./run.sh --rebuild     # force a clean frontend rebuild
PORT=9000 ./run.sh     # override any setting via environment variables
```

The script:
- runs `npm install` only if `frontend/node_modules` is missing, then
  `npm run build` only if `frontend/dist` is absent, stale, or `--rebuild` is
  passed;
- auto-installs backend deps (`pip install -e backend/`) if imports fail;
- prefers `python3.12`, falling back to `python3`;
- serves the built frontend from `frontend/dist` and the API from the same
  process.

Then open <http://127.0.0.1:6006>.

| -------------------------- | --------------------------- | ---------------------------------------- |

| `LOG_LEVEL`                | `INFO`                      | Logging level                            |

## What it does

- **Discovery** — recursively scans `PROFILE_ROOT` for `*.json.gz` / `*.json`,
  registers new files, and re-parses files that change. A watchdog observer plus
  a periodic rescan provide near-real-time detection.
- **Partial-file protection** — a file is only parsed once its size is stable
  across `FILE_STABILITY_CHECK_DELAY`; transient parse failures are retried.
- **Parsing** — decompresses and normalizes the Chrome-trace `traceEvents`,
  preserving every raw field (reconstructable losslessly).
- **Step detection** — parses `step[DECODE bs=1]`, `step[EXTEND bs=1 toks=107]`,
  … annotations into numbered steps with stage / batch size / token count.
- **Event attribution** — CPU events are attributed by timestamp containment;
  GPU kernels are attributed through the profiler `correlation` id to the
  `cudaLaunchKernel` that launched them, so asynchronous GPU work is attributed
  to the step that *launched* it (not the step that happens to be running when
  it executes).
- **Semantic mapping** — declarative YAML rules (`mappings/`) classify raw
  kernel / op names into semantic categories with a confidence level and a
  source-code reference. Precedence: `exact > qualified_exact > regex >
  contains > contains_any`; unknown events are kept and labelled `UNKNOWN`.
- **Aggregation** — per-step wall duration, GPU-busy (union of GPU intervals),
  per-category GPU duration sums, kernel counts, and top kernels.
- **Live updates** — a WebSocket (`/api/ws`) pushes
  `profile_discovered / profile_parsing / profile_ready / profile_failed /
  profile_removed / monitor_status` events; the UI updates without a reload.
  An *auto-follow* toggle controls whether a new profile becomes the active one.

### A note on async GPU timing

GPU kernels are launched by the CPU during a step but execute asynchronously on
the GPU. In a busy server the GPU may be queued, so a kernel launched inside a
0.9 ms decode step can execute several milliseconds later. The timeline
preserves the **actual** GPU execution timestamps (the spec forbids altering
timestamps), so the x-axis extends beyond the CPU step window to show where the
GPU work really ran. The CPU step window is drawn as a shaded background for
reference.

## API

| Method | Path                                        | Description                          |
| ------ | ------------------------------------------- | ------------------------------------ |
| GET    | `/api/health`                               | Health + monitor status              |
| GET    | `/api/categories`                           | Semantic category taxonomy           |
| GET    | `/api/profiles`                             | List profiles                        |
| GET    | `/api/profiles/{id}`                        | Profile summary + stage summary      |
| GET    | `/api/profiles/{id}/steps?stage=DECODE`     | Step summaries (optional stage filter) |
| GET    | `/api/profiles/{id}/steps/{stepId}`         | Step detail: metrics + timeline events |
| GET    | `/api/profiles/{id}/events/{eventId}`       | Event detail: raw + semantic + source + flows |
| WS     | `/api/ws`                                   | Real-time profile / monitor events   |

## Semantic mapping

Rules live in `mappings/` (YAML). Each rule has an `id`, `display_name`,
`category`, a `match` strategy, an optional `source` reference, and a
`confidence`. Example:

```yaml
- id: sglang.kvcache.store
  display_name: KV Cache Store
  category: KV_CACHE
  framework: sglang
  match:
    qualified_exact: ["sglang::store_kvcache"]
  confidence: high
  source:
    repository: sglang
    path: python/sglang/kernels/jit/csrc/elementwise/kvcache.cuh
    symbol: store_kvcache
    description: Stores K/V into the paged KV cache.
```

Add a new rule by appending to (or creating a file in) `mappings/`; the backend
picks it up on restart. Every new rule should come with a test in
`backend/tests/test_semantic_mapper.py`.

Categories: `SCHEDULER, EMBEDDING, RMSNORM, ROPE, QKV_PROJECTION,
Q_PROJECTION, K_PROJECTION, V_PROJECTION, O_PROJECTION, ATTENTION, KV_CACHE,
LINEAR, MLP, ACTIVATION, SAMPLING, MEMORY, SYNCHRONIZATION, OTHER, UNKNOWN`.

## Tests

```bash
cd backend
python3.12 -m pytest tests/ -q
```

Covers: gzip/JSON parsing + error classification, pid detection, step-name
parsing, step detection + correlation-based attribution, semantic matching
(precedence, qualified-exact with templates, unknown fallback), and aggregation
(interval union, per-category sums). A synthetic golden trace is generated by
`scripts/make_golden_fixture.py` into `fixtures/profile/golden/`.
