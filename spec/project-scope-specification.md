# SGLang Profiler Viewer — Project Scope Specification

> **Document purpose:** This document defines the product scope and required behavior of the first version of a local SGLang Profiler Viewer.  
> **Audience:** AI coding agents, developers, reviewers, and future maintainers.  
> **Important:** This is a **requirements / scope document**, not an implementation guide. Technology choices should only be made after these requirements are accepted.

---

## 1. Project Overview

### 1.1 Project name

**SGLang Profiler Viewer**

### 1.2 Project objective

Build a local web application that reads profile logs generated by SGLang `bench_serving --profile`, continuously discovers newly generated profile files, maps low-level profiler events to understandable SGLang concepts/source-code locations, and renders the profiling result as an easy-to-understand visual timeline.

The application must solve two problems:

1. **Profiler data discovery**
   - Automatically detect new profile files.
   - Automatically refresh the UI when new profile data becomes available.
   - Avoid requiring the user to manually restart or reload the viewer.

2. **Profiler data comprehension**
   - Hide or normalize the large amount of low-level C++ / CUDA template names.
   - Present events using meaningful SGLang concepts.
   - Provide a mapping back to the relevant SGLang source-code implementation.
   - Visualize execution timing in a way that is easier to understand than raw Chrome Trace output.

# 2. Current Input Environment

The initial version of the application must support profile data produced by a command similar to:

```bash
PYTHONPATH=$PWD/python \
FLASHINFER_DISABLE_VERSION_CHECK=1 \
SGLANG_TORCH_PROFILER_DIR=/root/.cache/profile_log \
/usr/bin/python3.12 -m sglang.bench_serving \
  --backend sglang \
  --host 127.0.0.1 \
  --port 11435 \
  --model my-local-model \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 128 \
  --num-prompts 10 \
  --max-concurrency 2 \
  --profile
```

The viewer must treat the profile directory as an input source rather than assuming that a single fixed profile file exists.

A typical directory structure may look like:

```text
/root/.cache/profile_log/
├── 1787442691.4637334/
│   └── 1787442691.464980-2.json.gz
├── 1787442757.5754936/
│   └── 1787442757.5764936-2.json.gz
└── ...
```

The exact timestamp and file names must not be hard-coded.

# 3. Scope

## 3.1 In scope

The first product version must include:

1. Local web UI.
2. Local profile-directory configuration.
3. Discovery of SGLang profile files.
4. Parsing of compressed profile traces.
5. Automatic detection of newly generated files.
6. Automatic refresh/update of the UI.
7. SGLang-aware semantic classification of profiler events.
8. Mapping from raw profiler event names to high-level SGLang concepts.
9. Mapping from semantic operations to SGLang source-code locations.
10. Prefill / Decode / Extend stage recognition where the trace provides sufficient information.
11. Decode-step visualization.
12. Batch-size display.
13. Duration display.
14. Timeline visualization.
15. Event detail view.
16. Raw event information access for debugging.
17. Filtering/searching of profile events.
18. Basic error handling for malformed or unsupported profile files.

## 3.2 Explicitly out of scope for the initial version

The first version should NOT attempt to solve all profiler scenarios.

The following are out of scope unless explicitly added in a later specification:

- Nsight Systems trace parsing.
- Nsight Compute report parsing.
- vLLM trace parsing.
- TensorRT-LLM trace parsing.
- Distributed multi-node trace visualization.
- Multi-GPU semantic analysis.
- Network/RDMA analysis.
- General-purpose Chrome Trace replacement.
- Full source-code browser/editor.
- Automatic performance optimization.
- Automatic source-code modification.
- Automatic benchmark execution.
- Automatic SGLang server startup.
- Remote multi-user deployment.
- Cloud-hosted profile analysis.

The initial product should stay focused on:

> **Local SGLang + `bench_serving --profile` + human-readable performance visualization.**

# 4. Primary User Scenario

The main expected workflow is:

```text
1. Start SGLang server
        ↓
2. Start bench_serving --profile
        ↓
3. SGLang generates profile files
        ↓
4. Viewer is already running
        ↓
5. Viewer detects new profile file
        ↓
6. Viewer parses the profile
        ↓
7. Viewer identifies SGLang stages
        ↓
8. Viewer maps low-level events to semantic operations
        ↓
9. Viewer updates the UI
        ↓
10. User inspects Decode / Prefill performance
```

The user should not need to:

```text
stop viewer
→ manually copy profile
→ restart viewer
→ refresh browser
```

for every new profile result.

# 5. Requirement #1 — Local Web Application

## 5.1 Requirement

The system must run as a local web application.

The expected architecture is:

```text
User Browser
     │
     ▼
Local Web Application
     │
     ▼
Local Profile Directory
```

The initial product is intended to be used on the same machine or development environment where SGLang profiling data is available.

## 5.2 Local-only requirement

The initial version must not require a cloud service.

The application should work without sending profiler data to external services.

## 5.3 Startup behavior

The application should provide a simple startup mechanism such as:

```text
start viewer
    ↓
open http://localhost:<port>
```

The exact language/framework/port is intentionally left to a later technical-design document.

## 5.4 Browser UI expectations

The UI should be a modern web application rather than a raw JSON viewer.

The user should immediately see:

- currently loaded profile sessions,
- number of discovered profile files,
- selected profile,
- stage/step information,
- timeline,
- event details,
- application status.

---

# 6. Requirement #2 — Read SGLang Profile Logs

## 6.1 Supported input

The viewer must read profile logs generated by SGLang `bench_serving --profile`.

The viewer must support compressed JSON traces such as:

```text
*.json.gz
```

The viewer must not rely on a single fixed file name.

## 6.2 Directory discovery

The viewer must support a configurable profile root directory.

Example:

```text
/root/.cache/profile_log/
```

The viewer must discover:

```text
profile_root/
    <run directory>/
        <trace file>
```

The exact directory structure should be discovered rather than hard-coded wherever practical.

## 6.3 File discovery rules

The implementation must define:

- supported file extensions,
- supported compression formats,
- what counts as a valid profile file,
- what counts as a completed profile file,
- what happens when a file is still being written,
- how duplicate files are detected,
- how already-processed files are tracked.

## 6.4 Partial-file protection

The viewer must not attempt to fully parse a profile file that is still being written if doing so could result in corrupted or incomplete data.

The implementation should use a safe strategy such as:

```text
new file detected
      ↓
wait / verify stable file size
      ↓
attempt parse
      ↓
success → add profile
failure → retry later / mark error
```

The exact strategy is a later technical-design concern, but this behavior is mandatory.

---

# 7. Requirement #3 — Real-Time Automatic Refresh

## 7.1 Requirement

The web UI must automatically detect newly generated profile files.

Example:

```text
Viewer running
    │
    │
    ├── profile_001.json.gz
    │
    ├── profile_002.json.gz
    │
    ▼
SGLang benchmark continues
    │
    ▼
profile_003.json.gz appears
    │
    ▼
Viewer detects profile_003
    │
    ▼
UI updates automatically
```

The user should not have to reload the browser manually.

## 7.2 Update behavior

When a new valid profile appears:

1. Detect it.
2. Parse it.
3. Validate it.
4. Add it to the profile-session list.
5. Update the UI state.
6. If auto-follow mode is enabled, display the new profile automatically.
7. Do not discard existing profiles.

## 7.3 Real-time status

The UI should clearly indicate whether monitoring is active.

Example:

```text
● Monitoring
Last scan: 21:33:12
Profiles: 7
New files: 1
```

The user should be able to understand whether the viewer is actively watching the profile directory.

## 7.4 Auto-follow behavior

The UI should distinguish between:

### Auto-follow ON

New profiles become the active profile automatically.

### Auto-follow OFF

New profiles are detected and listed, but the current profile remains selected.

This prevents a user who is analyzing an older step from being forcibly moved to a new profile.

## 7.5 Refresh latency

The exact latency can be defined later, but the product should target near-real-time behavior.

The requirement is:

> A newly completed profile should become visible in the UI shortly after it appears in the profile directory without manual page reload.

# 8. Requirement #4 — SGLang-Aware Profiler Semantic Mapping

This is the **core requirement of the project**.

## 8.1 Problem statement

Raw profiler names are often too low-level and too long to be useful.

Examples:

```text
void at::native::reduce_kernel<512, ...>
void flashinfer::norm::RMSNormKernel<...>
cublas::Kernel<...gemm...>
void sglang::fused_rope_kernel<...>
void sglang::store_kvcache<...>
void flashinfer::BatchPrefillDecodeKVCacheKernel<...>
```

The viewer must not present these raw names as the primary user-facing representation.

Instead, the user should see meaningful names such as:

```text
RMSNorm
QKV Projection
RoPE
KV Cache
Attention
O Projection
MLP
Sampling
```

## 8.2 Semantic mapping must be defined before UI implementation

The project must first define a semantic mapping specification that relates:

```text
SGLang source code
        ↓
known operation / stage
        ↓
profiler annotation
        ↓
CUDA / FlashInfer / cuBLAS event
        ↓
human-readable category
```

The UI must consume this semantic model rather than implementing ad-hoc function-name parsing inside visual components.

## 8.3 Semantic layer

At minimum, the semantic model should support concepts such as:

```text
Scheduler
Prefill
Decode
Extend
Embedding
RMSNorm
RoPE
Q Projection
K Projection
V Projection
QKV Projection
Attention
KV Cache
O Projection
MLP
Activation
Sampling
Memory
Synchronization
Other
```

The exact taxonomy may evolve, but it must be explicitly documented.

## 8.4 Source-code mapping

Every important semantic category should have a source-code mapping where practical.

Example concept:

```text
KV Cache
    ↓
SGLang implementation
    ↓
sglang::store_kvcache
    ↓
Raw profiler kernel
```

Another example:

```text
Attention
    ↓
FlashInfer attention implementation
    ↓
BatchPrefillDecodeKVCacheKernel
    ↓
Raw profiler event
```

The source mapping should answer:

> "If I see this event in the profiler, where in SGLang should I look?"

## 8.5 Mapping must be version-aware

SGLang changes over time.

Therefore, semantic mapping should not assume that one function name remains valid forever.

The system should support a concept similar to:

```text
SGLang version
    ↓
mapping rules
    ↓
raw profiler names
```

The initial version may support one known SGLang source revision, but the architecture must allow mappings to evolve.

## 8.6 Confidence / fallback

Not every profiler event will be recognized.

The semantic system must therefore support:

```text
Known
Probably known
Unknown
```

Unknown events must not crash the viewer.

Example:

```text
Unknown Kernel
raw:
void some_future_kernel<...>

category:
Other / Unknown
```

The raw name should still be accessible.

# 9. Requirement #5 — Elegant Visualization

The viewer must provide a much more readable visualization than a raw profiler trace.

## 9.1 Primary visualization goal

A user should be able to understand one Decode step at a glance.

Desired conceptual representation:

```text
┌──────────────────────────────────────────────┐
│ Decode Step #42         BS=1        12.81ms │
├──────────────────────────────────────────────┤
│                                              │
│ Scheduler       ███                          │
│ RMSNorm            ██                        │
│ QKV Projection       █████                   │
│ RoPE                    █                     │
│ KV Cache                 ██                  │
│ Attention                  ████              │
│ O Projection                   ██            │
│ MLP                             ███████       │
│ Sampling                              █       │
│                                              │
└──────────────────────────────────────────────┘
```

This exact appearance is illustrative, not a fixed implementation.

The important requirements are:

- clear hierarchy,
- readable semantic names,
- visible duration,
- visible order,
- visible relationship between operations,
- ability to inspect details,
- visually distinguish different types of operations.

## 9.2 Step summary

Each SGLang execution step should expose at least:

```text
Step type:
DECODE / PREFILL / EXTEND / ...

Step number:
#42

Batch size:
1

Start time:
...

Duration:
12.81 ms
```

## 9.3 Timeline

The visualization must preserve temporal relationships.

It should show:

```text
start time
duration
ordering
overlap
```

The viewer must not turn a parallel execution into a misleading sequential list.

## 9.4 Semantic color/grouping

The UI should visually group categories.

For example:

```text
Normalization
Position Encoding
Attention
KV Cache
Linear/GEMM
MLP
Sampling
Scheduler
Other
```

The final color palette will be defined in the UI specification.

## 9.5 Detail inspection

Clicking an event should reveal details such as:

```text
Semantic:
Attention

Raw profiler name:
flashinfer::BatchPrefillDecodeKVCacheKernel<...>

Duration:
1.82 ms

Start:
...

Parent:
Decode Step #42

Backend:
FlashInfer

Source mapping:
...

Confidence:
High
```

The UI must provide both:

- human-readable semantic information,
- original raw information.

# 10. Primary Information Hierarchy

The viewer should present information from high-level to low-level.

The preferred hierarchy is:

```text
Profile Session
    ↓
Execution Stage
    ↓
Step
    ↓
Semantic Operation
    ↓
Framework Operation
    ↓
GPU Kernel
    ↓
Raw Profiler Event
```

Example:

```text
Profile Run #7
    ↓
DECODE
    ↓
Decode Step #42
    ↓
Attention
    ↓
FlashInfer
    ↓
BatchPrefillDecodeKVCacheKernel
    ↓
raw JSON event
```

The user should not be forced to start from the raw kernel name.

# 12. User Interaction Requirements

The first version should support:

## 12.1 Select profile

User can choose which profile run to inspect.

## 12.2 Select step

User can choose a specific Prefill / Decode / Extend step.

## 12.3 Zoom timeline

User can zoom into a step.

## 12.4 Pan timeline

User can move through a large timeline.

## 12.5 Select event

Clicking an event shows detailed information.

## 12.6 Search

User can search for:

```text
Attention
RMSNorm
GEMM
KV Cache
Decode
```

and optionally raw function names.

## 12.7 Filter

User should be able to filter categories such as:

```text
Attention only
GEMM only
KV Cache only
Unknown only
```

## 12.8 Raw-name inspection

The user must always be able to access the original profiler function name.

This is required because the semantic mapping can never be assumed to be perfect.

# 13. Correctness Requirements

The viewer must never silently invent profiler meaning.

Important rules:

1. Do not claim a kernel is "Attention" solely because the name looks similar if the mapping is uncertain.
2. Preserve the original raw event.
3. Expose mapping confidence where appropriate.
4. Do not merge unrelated events without an explicit rule.
5. Do not change timestamps.
6. Do not alter durations.
7. Do not hide events merely because they are currently classified as unknown.
8. Do not present an aggregate number without defining how it was calculated.

The viewer is a profiler interpretation tool, not a source of fabricated performance data.

---

# 14. Performance Requirements

Profiler traces can become large.

The first version must be designed with the expectation that a profile may contain a very large number of events.

The application should therefore avoid:

```text
create one heavy UI DOM element per event
```

for very large traces.

The technical design should consider:

- incremental parsing,
- Web Worker processing,
- event indexing,
- viewport-based rendering,
- lazy loading,
- cached semantic classification,
- efficient search.

However, the exact implementation is not part of this scope document.

---

# 15. Reliability Requirements

## 15.1 Invalid file

If a profile file is malformed:

```text
Profile #7
Status: Parse Error
Reason: Invalid gzip / JSON
```

The viewer must continue monitoring other files.

## 15.2 Unsupported event

Unknown event:

```text
category = UNKNOWN
```

must not crash the application.

## 15.3 Unsupported SGLang version

The viewer should report:

```text
SGLang semantic mapping not fully supported
```

instead of pretending that mappings are guaranteed to be correct.

## 15.4 New trace schema

If a newer trace contains fields the viewer does not know:

- preserve what can be preserved,
- ignore unsupported optional fields safely,
- report compatibility limitations.

# 16. Acceptance Criteria — MVP

The first version should be considered functionally complete only when all of the following are true.

## A. Local Web

- Viewer can start locally.
- Browser can access it through localhost.
- No external cloud service is required.

## B. Profile Discovery

Given:

```text
/root/.cache/profile_log/
```

the viewer can discover existing profile files.

## C. Profile Parsing

Given a valid SGLang `.json.gz` trace, the viewer can:

- decompress it,
- parse it,
- identify profiler events,
- identify relevant SGLang annotations.

## D. Real-Time Discovery

While the viewer is running:

```text
new .json.gz appears
        ↓
viewer detects it
        ↓
profile list updates
```

without manual browser reload.

## E. SGLang Semantics

The viewer can classify at least a first set of important events, including concepts such as:

```text
Decode
Prefill / Extend where present
RMSNorm
RoPE
KV Cache
Attention
GEMM / Linear
MLP
Sampling
Unknown
```

## F. Source Mapping

For supported semantic events, the viewer provides a mapping to the corresponding SGLang implementation or source-code concept.

## G. Visualization

A selected Decode step can be presented in a readable timeline such as:

```text
Decode Step #42
BS=1
12.81 ms

Scheduler
RMSNorm
QKV Projection
RoPE
KV Cache
Attention
O Projection
MLP
Sampling
```

## H. Raw Data Access

Clicking an event provides access to its raw profiler information.

## I. Stability

One malformed profile file must not stop monitoring of future profile files.

# 19. Recommended Product Principle

The most important design principle is:

> **The viewer should explain the profiler data instead of merely displaying the profiler data.**

Raw profiler tools already provide:

```text
kernel name
timestamp
duration
thread
stream
```

The SGLang Profiler Viewer adds:

```text
SGLang meaning
    ↓
semantic operation
    ↓
source-code relationship
    ↓
human-readable timeline
```

Therefore, the project should optimize for **understanding**, not simply for reproducing Chrome Trace.
