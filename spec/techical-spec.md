# SGLang Profiler Viewer — Technical Specification

## 1. Document Purpose

This document defines the technical architecture and implementation requirements for **SGLang Profiler Viewer**.

It follows the product requirements in `project-scope-specification.md`.

The system is intended to consume profile traces generated by:

```bash
PYTHONPATH=$PWD/python \
FLASHINFER_DISABLE_VERSION_CHECK=1 \
SGLANG_TORCH_PROFILER_DIR=/root/.cache/profile_log \
/usr/bin/python3.12 -m sglang.bench_serving \
  --backend sglang \
  --host 127.0.0.1 \
  --port 11435 \
  --model my-local-model \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 128 \
  --num-prompts 10 \
  --max-concurrency 2 \
  --profile
```

The system must provide:

- local web UI,
- local filesystem profile discovery,
- compressed profile parsing,
- real-time new-file detection,
- SGLang-aware semantic mapping,
- source-code-oriented interpretation,
- readable timeline visualization,
- event detail inspection,
- scalable handling of large traces.

This document describes **how the system should be implemented**.

# 3. Architectural Principles

## 3.1 Separation of concerns

The system must separate:

```text
Raw profiler data
        ↓
Parsing
        ↓
Normalized trace model
        ↓
Semantic classification
        ↓
Performance aggregation
        ↓
API model
        ↓
Visualization
```

Frontend components must not directly parse raw PyTorch Profiler JSON.

## 3.2 Deterministic parsing

Parsing and semantic classification should be deterministic.

The same input trace and same mapping configuration must produce the same normalized representation.

Do not use an LLM as the primary parser.

## 3.3 AI as an analysis layer

AI may later be used for:

- explanations,
- summaries,
- bottleneck analysis,
- anomaly interpretation,
- source-code explanation.

AI must not be the authoritative source for timestamps, durations, event relationships, or semantic mappings that can be defined deterministically.

## 3.4 Raw data preservation

The system must preserve the original profiler event information.

Normalization must be additive rather than destructive.

A normalized event should contain:

```text
rawName
normalizedName
semanticCategory
sourceMapping
timing
relationships
```

rather than replacing the raw name.

## 3.5 Incremental architecture

New profile files must be incorporated without restarting the backend.

# 5. Backend Technical Design

# 5.1 FastAPI application

FastAPI is the application boundary for:

- serving the frontend in production if desired,
- providing profile metadata,
- providing detailed trace data,
- exposing semantic information,
- broadcasting filesystem changes through WebSocket.

Example conceptual application:

```python
app = FastAPI()

app.include_router(profile_router)
app.include_router(event_router)
app.include_router(websocket_router)
```

The application should avoid storing huge raw traces directly inside global request state.

---

Backend configuration should include:

```text
PROFILE_ROOT
HOST
PORT
WATCH_INTERVAL
FILE_STABILITY_CHECK_DELAY
MAX_LOADED_PROFILES

LOG_LEVEL
```

Example:

```bash
PROFILE_ROOT=/root/.cache/profile_log
HOST=127.0.0.1

```

Configuration must not be hard-coded.

## 5.2.1 Profile root resolution

Priority:

1. CLI argument

3. configuration file

Example default:

```text
/root/.cache/profile_log
```

should be treated as a convenience default, not an immutable path.

# 6. Profile Discovery

## 6.1 Discovery model

The backend maintains a profile registry.

Conceptually:

```python
ProfileRegistry:
    discovered
    parsing
    ready
    failed
```

Each filesystem profile must have a stable identifier.

Recommended:

```text
profile_id = hash(canonical_path + file_size + modification_time)
```

or a deterministic path-based identifier.

The identifier must remain stable during one viewer session.

---

# 6.2 Initial scan

At startup:

```text
start application
      ↓
validate PROFILE_ROOT
      ↓
recursive scan
      ↓
find candidate profile files
      ↓
check file stability
      ↓
parse valid files
      ↓
populate registry
      ↓
start watcher
```

The watcher must not be started as a replacement for the initial scan.

Both are required.

---

# 6.3 File watcher

Use `watchdog` or an equivalent filesystem notification mechanism.

Events of interest:

- created,
- moved,
- modified.

The system should primarily treat a new completed `.json.gz` as a new profile.

Because a file can be created before writing is complete, creation alone is not sufficient.

---

# 6.4 File stability

Before parsing:

```text
file detected
     ↓
record size
     ↓
wait
     ↓
check size
     ↓
size unchanged?
   yes → parse
   no  → wait again
```

The implementation should avoid arbitrary long blocking waits.

If parsing fails because a file is incomplete:

```text
FAILED_TEMPORARY
```

may be retried.

A permanent parse failure should become:

```text
FAILED
```

with an error message.

---

# 6.5 New-profile WebSocket event

When a new profile becomes READY:

```json
{
  "type": "profile_added",
  "profileId": "...",
  "timestamp": "...",
  "status": "ready"
}
```

The frontend must react to this without a browser reload.

Additional event types:

```text
profile_discovered
profile_parsing
profile_ready
profile_failed
profile_removed

```

# 7. Trace Parser

## 7.1 Input

Primary input:

```text
*.json.gz
```

## 7.2 Processing pipeline

```text
file
 ↓
gzip decompression
 ↓
JSON decoding
 ↓
schema validation
 ↓
event extraction
 ↓
metadata extraction
 ↓
normalized trace
```

---

# 7.3 Parser responsibilities

The parser must:

- decompress the file,
- parse JSON,
- identify `traceEvents`,
- preserve supported fields,
- normalize timestamps,
- normalize durations,
- identify process/thread metadata,
- identify GPU-related events,
- identify flow events,
- identify SGLang annotations,
- tolerate unknown fields.

The parser must NOT:

- assign semantic meaning without the semantic-mapping layer,
- silently drop events,
- modify timing values.

---

# 7.4 Trace timestamp normalization

Raw profiler timestamps should be retained exactly.

A derived relative timestamp may also be computed:

```text
relative_ts = event.ts - trace_start_ts
```

Both should be available.

Recommended units internally:

```text
microseconds
```

because profiler traces commonly operate at microsecond precision.

Frontend display may convert to:

```text
ns
μs
ms
s
```

depending on zoom level.

---

# 7.5 Event normalization

Internal normalized event:

```python
class TraceEvent:
    id: str
    name: str
    raw_name: str
    category: str | None
    phase: str | None
    timestamp_us: float
    duration_us: float | None

    process_id: int | None
    thread_id: int | None

    args: dict

    semantic_category: str | None
    semantic_name: str | None

    stage_id: str | None
    step_id: str | None

    parent_event_id: str | None

    flow_ids: list[str]

    source_mapping_id: str | None
    confidence: str | None
```

The exact implementation may use Pydantic models or dataclasses.

# 8. Trace Hierarchy

The normalized trace must support this hierarchy:

```text
Profile
  └── Execution stages
       ├── PREFILL
       ├── EXTEND
       └── DECODE
            ├── Step #1
            ├── Step #2
            └── Step #3
                 ├── Scheduler
                 ├── Attention
                 ├── KV Cache
                 ├── GEMM
                 ├── MLP
                 └── ...
```

This hierarchy is derived data.

The raw events remain the source of truth.

# 9. Step Detection

## 9.1 SGLang annotation detection

The initial implementation should detect annotations such as:

```text
step[DECODE bs=1]
step[DECODE bs=2]
step[EXTEND bs=1]
```

The parser should not assume that only these exact strings will exist forever.

Use a rule-based parser:

```text
step[
    STAGE
    optional attributes
]
```

## 9.2 Step model

Example:

```python
class ExecutionStep:
    id: str
    index: int
    stage: Literal["PREFILL", "DECODE", "EXTEND", "UNKNOWN"]
    batch_size: int | None

    start_us: float
    duration_us: float

    event_ids: list[str]
```

## 9.3 Step grouping

Events inside a step should be grouped using timing and profiler relationships.

The technical implementation must document exactly which events are considered children of a step.

Do not simply assign every event whose timestamp falls between start/end if doing so causes unrelated asynchronous GPU work to be incorrectly attributed.

# 10. Semantic Mapping System

This is the most important technical subsystem.

## 10.1 Goal

Convert raw event names such as:

```text
flashinfer::norm::RMSNormKernel<...>
sglang::fused_rope_kernel<...>
sglang::store_kvcache<...>
cublas::Kernel<...gemm...>
flashinfer::BatchPrefillDecodeKVCacheKernel<...>
```

into:

```text
RMSNorm
RoPE
KV Cache
GEMM
Attention
```

and then map those concepts toward the SGLang source implementation.

---

# 10.2 Mapping must be externalized

Do not hard-code all mapping rules inside Python source files.

Prefer declarative mapping files.

Example:

```yaml
- id: sglang.kv_cache.store
  category: KV_CACHE
  display_name: KV Cache Store
  match:
    contains:
      - "sglang::store_kvcache"
  framework: sglang
  source:
    repository: sglang
    path: ...
  confidence: high
```

This allows mapping rules to be updated independently.

---

# 10.3 Mapping structure

Each mapping rule should support:

```text
id
display_name
category
stage
framework
match strategy
match pattern
source mapping
confidence
version constraints
description
```

Example:

```yaml
id: attention.flashinfer.decode_kv_cache
display_name: Attention
category: ATTENTION
framework: flashinfer

match:
  contains:
    - "BatchPrefillDecodeKVCacheKernel"

source:
  repository: flashinfer
  symbol: BatchPrefillDecodeKVCacheKernel

confidence: high
```

---

# 10.4 Mapping precedence

Rules must be deterministic.

Recommended precedence:

```text
exact match
    ↓
qualified exact match
    ↓
regex match
    ↓
contains match
    ↓
category heuristic
    ↓
unknown
```

The first matching rule should be explicitly determined by priority.

Do not depend on YAML file order unless documented.

---

# 10.5 Semantic classification output

Example:

```json
{
  "semanticCategory": "ATTENTION",
  "semanticName": "Attention",
  "framework": "flashinfer",
  "confidence": "high",
  "mappingRuleId": "attention.flashinfer.decode_kv_cache",
  "sourceMappingId": "..."
}
```

---

# 10.6 Unknown event handling

Unknown events must remain visible.

Example:

```text
UNKNOWN
raw:
void future_kernel<...>
```

The UI should show:

```text
Unknown
```

not invent a meaning.

# 11. Source-Code Mapping

## 11.1 Goal

A semantic operation should be associated with the relevant SGLang source-code concept.

The viewer should eventually be able to display:

```text
KV Cache
SGLang
store_kvcache
source path:
python/...
```

or:

```text
Decode Scheduler
SGLang
Scheduler.run_batch(...)
source path:
python/sglang/...
```

## 11.2 Version-awareness

Mapping files should optionally contain:

```yaml
sglang_version:
  min: ...
  max: ...
git_commit:
  - ...
```

If the mapping cannot be verified against the trace's source version:

```text
confidence = unknown
```

should be possible.

# 12. CPU/GPU Correlation

## 12.1 Goal

The viewer must eventually connect:

```text
SGLang event
   ↓
CPU / Python operation
   ↓
CUDA launch
   ↓
GPU kernel
```

This is required for meaningful analysis.

## 12.2 Flow model

Normalized representation:

```python
class EventFlow:
    id: str
    source_event_id: str
    destination_event_id: str
```

The viewer should preserve profiler flow information where available.

## 12.3 UI behavior

A selected semantic operation should allow the user to inspect related lower-level events.

Example:

```text
Attention
  ↓
CPU op
  ↓
CUDA launch
  ↓
FlashInfer kernel
```

# 13. Performance Aggregation

## 13.1 Goal

Aggregate low-level events into meaningful timing metrics.

Example:

```text
Decode Step
Total: 12.81 ms

Attention: 1.82 ms
GEMM:      3.21 ms
MLP:       4.12 ms
KV Cache:  0.31 ms
Other:     3.35 ms
```

## 13.2 Critical rule

Do not assume:

```text
sum(all event durations) == step duration
```

because events may overlap.

The implementation must distinguish:

- wall-clock duration,
- sum of event durations,
- GPU busy interval,
- exclusive duration where calculable,
- overlap.

## 13.3 Recommended metrics

For each step:

```text
wall_duration_us
cpu_duration_us
gpu_busy_duration_us
semantic_duration_by_category
kernel_count
unknown_event_count
```

Optional:

```text
overlap_ratio
idle_gap_duration
```

# 19. Live Update Architecture

The intended flow:

```text
SGLang
  ↓
new profile file
  ↓
OS file notification
  ↓
watchdog
  ↓
ProfileManager
  ↓
parse
  ↓
semantic classify
  ↓
aggregate
  ↓
WebSocket event
  ↓
React
  ↓
profile list update
```

## 19.1 Important requirement

The frontend must not repeatedly download every profile after each change.

A new profile event should trigger a targeted API call.

Example:

```text
WS:
profile_ready(profile-009)

Frontend:
GET /api/profiles/profile-009
```

This avoids unnecessary bandwidth and computation.

# 20. Caching

## 20.1 Backend cache

The backend should cache parsed profiles.

A profile should not be reparsed every time the user switches between steps.

Conceptual:

```text
ProfileFile
    ↓
ParsedTraceCache
    ↓
StepIndex
    ↓
SemanticEventIndex
```

## 20.2 Cache invalidation

When a profile file changes:

```text
old cache invalid
    ↓
verify file completion
    ↓
reparse
```

For completed immutable profile files, parsing should occur only once.

---

# 21. Large Trace Strategy

Large traces are expected.

## 21.1 Do not send everything to frontend

The backend should expose:

```text
summary
step index
semantic event summary
```

before exposing:

```text
full raw event data
```

## 21.2 Lazy loading

Example:

```text
User selects Decode #42
        ↓
Backend loads / returns detailed events for #42
        ↓
Frontend renders selected step
```

This avoids sending unrelated events.

## 21.3 Pagination

Large lists should support pagination or range queries where necessary.

# 26. AI Integration Boundary

AI integration should be optional.

The core viewer must work without an external AI provider.

AI can receive a structured representation such as:

```json
{
  "step": {
    "stage": "DECODE",
    "batchSize": 1,
    "durationMs": 12.81
  },
  "operations": [
    {
      "category": "ATTENTION",
      "durationMs": 1.82
    },
    {
      "category": "MLP",
      "durationMs": 4.12
    }
  ]
}
```

AI should generate:

```text
summary
bottleneck explanation
suspicious patterns
possible causes
```

AI must not be responsible for calculating the authoritative timing.

# 30. Definition of Done

The technical implementation is complete when:

1. FastAPI backend starts locally.
2. React frontend starts locally.
3. Backend discovers SGLang profile `.json.gz`.
4. Profile files are safely parsed.
5. Parsed data is normalized.
6. SGLang stages are detected.
7. Decode batch size is detected.
8. Important events are semantically mapped.
9. Unknown events remain visible.
10. Source-code mapping is available for supported events.
11. Decode timeline is rendered.
12. Event details are inspectable.
13. New profile files are detected automatically.
14. UI updates through WebSocket without page reload.
15. Large traces are handled without obvious UI blocking.
16. Golden traces and regression tests pass.
17. No core functionality depends on an external AI service.

The central engineering principle is:
